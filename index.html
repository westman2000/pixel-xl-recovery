Pixel XL clock recovery investigation and toolkit

An instrumented case study of a first-generation Google Pixel XL, codename marlin, that repeatedly failed to boot. A two-core boot option first restored Android. Further experiments restored all four cores using alternate CPU PLLs, corrected output dividers, and conservative frequency limits.

Start with the case study to read the investigation, or the recovery runbook to follow the diagnostic sequence. All documentation is in English.

[Read the website](https://westman2000.github.io/pixel-xl-recovery/) · [Download the latest release](https://github.com/westman2000/pixel-xl-recovery/releases/latest) · Report a result or problem · Host checks

For the single offline reading copy, download and extract the release archive, then open READ-ME.html in a browser. GitHub displays HTML as source; the Markdown chapters above can be read directly on GitHub. Keep the extracted files together so the reader's evidence links work.

One physical device was tested. This is a documented workaround with a narrowly supported image builder, not a universal bootloop repair. The exact physical defect remains unknown. The results justify further investigation of the normal clock path; they do not prove that a particular transistor, solder joint, power rail, or PLL is damaged.

The retained configuration passed approximately 12 minutes of concurrent correctness workloads, 7,252 checksum and compression checks, 800,000 floating-point test iterations across four cores, three normal reboots, and ten display Dozing/Awake transitions. Maximum sampled battery temperature during its load runs was 39.0 °C. These are bounded tests, not evidence of months of reliable operation.

Only two data bytes in the decompressed kernel were changed for the divider correction. That is not the total size of the boot-image modification: command-line fields, device-tree frequency tables, compressed kernel bytes, layout offsets, and the legacy header checksum also changed.

The original boot already included lpm_levels.sleep_disabled=1. It was preserved. Display transitions are therefore not presented as proof of deep suspend or good standby battery life.

Compatibility before convenience

The offline builder accepts only an original boot image with this full SHA-256:

26d5c3e57bfcdd3b45f9d66e4ec7224cfca5ac43a003ff433f19288bd63bcf4c

That restriction protects against applying raw kernel offsets to a different binary. It is not a claim that every phone using this image can safely use the workaround. A matching image can still run on a phone with a different fault.

No boot images, kernel binaries, personal device identifiers, screenshots, or complete private logs are included. Obtain a backup of your own matching installation. If its hash differs, use the diagnostic tools and porting plan; do not change the expected hash merely to bypass the check.

This kit does not cover Pixel 2 or newer devices, the smaller sailfish Pixel, Nexus devices, locked bootloaders, modern vendor_boot/init_boot layouts, AVB signing, or arbitrary Snapdragon boards. Related hardware is a research lead, not a compatibility guarantee.

Quick offline reproduction

Requirements: Python 3.9 or newer and, for the four-core build, the LZ4 command-line program. The exact reconstruction was verified with LZ4 1.10.0. Standard-library Python is sufficient; no Python packages need to be installed.

Get the tools by extracting a release archive or cloning the repository:

git clone https://github.com/westman2000/pixel-xl-recovery.git
cd pixel-xl-recovery

Run these commands from the kit directory. Keep original images and generated outputs outside the public project:

python3 tools/inspect_boot.py ../private/boot-original.img

python3 tools/build_boot.py \
  --boot ../private/boot-original.img \
  --profile profiles/marlin-lineage22-case1.json \
  --variant rescue \
  --out ../private/rescue-build

python3 tools/build_boot.py \
  --boot ../private/boot-original.img \
  --profile profiles/marlin-lineage22-case1.json \
  --variant stable \
  --out ../private/stable-build

The builder never contacts a phone. It rejects existing output directories and writes an image only after the result matches the recorded case hash. “Stable” is the retained case variant name; it does not certify a new device.

Expected outputs:

rescue  7c6f9d632f45f5b5000e541cef5ae17b48b496e6d9135e5058578da0748cd8e8
stable  4635c2c76c37ff34259bfdc15d7e430c95cbc24cfd85cd864b877f0a21d2ccee

Read the runbook before installing either image. On the case device, fastboot boot rejected both the original and modified images with dtb not found; temporary boot was not an available escape hatch. Recovery was contained in the boot image, so modifying boot affected the recovery path too.

Finding and scope

A Pixel XL that had been unused for years was connected for experimental recovery. It could reach fastboot and recovery, but Android repeatedly failed to stay up. Restricting boot to CPU0 and CPU1 produced a usable Android session. Later, all four cores executed correct workloads after switching both CPU clusters to alternate PLLs, disabling ACD for that mode, correcting two alternate-PLL divider settings, and limiting the performance cluster to 902.4 MHz.

The retained configuration also limits CPU0/1 to 1,593.6 MHz. This prevents the approximately 1,996.8 MHz bursts observed when relying only on runtime limits. The owner explicitly preferred stability over maximum speed.

This is an experiment on one physical phone. It establishes a functioning workaround for that phone and image under the recorded tests. It does not establish the prevalence of the fault, prove the physical location of damage, or certify any other unit. No microscopic inspection, oscilloscope measurement, power-rail probing, solder repair, or exact source-rebuilt control kernel was part of the investigation.

Initial evidence

The preserved console from a failed Android boot contained 100 messages reporting that perfcl_pll did not lock. The captured boot ended around 50 seconds. It did not contain a conclusive panic explaining the reset. The matching message was:

PLL perfcl_pll didn't lock after enabling it!

A PLL is a circuit used to synthesize a clock frequency. In this context, “lock” indicates that the expected stabilized state was detected. A log saying that the lock condition was not reached identifies a clock-path problem worth investigating; it does not by itself identify a damaged component.

Recovery provided an important counterexample. All four CPUs could be online there for several minutes, with five early matching messages in its captured log. That observation made “both large cores are completely dead” an inadequate explanation.

The initial diagnosis remained a hypothesis: Android activity, clock changes, or a related mode transition appeared to expose a problem associated with the performance cluster's normal clock path. Different workloads and power states in recovery could matter. The observations did not isolate which of those differences was decisive.

Establishing a recovery baseline

The first useful boot modification appended:

nr_cpus=2 maxcpus=2

Only the boot-header command line changed. The compressed kernel, device trees, ramdisk, and original header ID were preserved. Android then booted and remained usable long enough to collect diagnostics and plan controlled experiments. CPU0/1 formed the practical recovery baseline.

This was more than a temporary runtime CPU-offline operation: the boot-time options limited the CPU set made available to the kernel. Runtime attempts to use unavailable CPUs were not assumed to be meaningful tests of their hardware.

The rescue image hash was:

7c6f9d632f45f5b5000e541cef5ae17b48b496e6d9135e5058578da0748cd8e8

This image remained the primary fallback throughout the campaign. The Android bootloader was already unlocked. The experiments did not establish a data-preserving way to unlock a locked device.

Temporary boot was attempted with both original and changed images; the bootloader rejected them with dtb not found. The investigation therefore used explicit writes to boot_a, followed by normal boot and verification. boot_b, system, and vendor were not flashed, and slots were not switched. The boot image also supplied recovery on this installation, so a fallback boot image and the ability to enter fastboot were essential.

Preliminary performance and battery observations

The two-core system was noticeably slower than a fully functioning four-core configuration would be expected to be. Several separate observations were made before the clock-path experiments:

  • CPU0/1 briefly accepted a near-2 GHz setting when both relevant runtime limits were adjusted. A narrow parallel SHA-256 workload improved by about 21% in that short comparison. The system subsequently restored the lower limit. This was not a whole-phone benchmark or a basis for a long-term overclock.
  • Some Android/vendor cpuset groups behaved poorly with only two CPUs available. Temporary two-core cpuset adjustments helped that restricted configuration. Those settings were not appropriate for the eventual four-core configuration, where the normal top-app group contained CPU0–3.
  • Rendering resolution was changed to 1080 × 1920 and animation scales to 0.5. These are UI changes, not repairs to CPU hardware. The final measured density override was 448; an earlier note recorded 420. The measured 448 setting was left alone rather than silently overwritten.
  • Battery temperature and charging data were readable. Full-charge capacity equalled the configured design value and cycle count was zero, but the device history and recent first-use metadata made those fields unsuitable for calculating battery health. No complete discharge-capacity test was performed.

These observations are retained because they explain earlier choices and prevent unrelated UI or battery changes from being credited with the clock recovery.

Finding the alternate clock path

Inspection of the reference clock driver identified an alternate-PLL mode and a corresponding ACD restriction. The boot options used were:

clock_cpu_8996.use_alt_pll=1 clock_cpu_8996.enable_acd=0

Both options matter. The reference CPU clock driver contains the alternate-parent selection and rejects the combination of alternate PLLs with ACD enabled. Here ACD refers to adaptive clock distribution, a separate part of the clock-control arrangement.

The options were not accepted merely because they appeared in a command line. Runtime checks read the module parameters and actual mux parents:

pwrcl_hf_mux parent  -> pwrcl_alt_pll
perfcl_hf_mux parent -> perfcl_alt_pll

The observation was encouraging but also confounded: the experiment changed the selected PLL path and the ACD mode. It therefore cannot separate a primary-PLL problem from an ACD-related issue, or a combination of the two.

Discovering the divide by two behavior

Early alternate-PLL experiments were slower than their reported frequency values suggested. Measuring clocks under load exposed the discrepancy:

Cluster Reported rate before correction Measured rate before correction
Efficient1,593.6 MHzApproximately 796.8 MHz
Performance902.4 MHzApproximately 451.2 MHz

Idle measurements were not reliable evidence of maximum frequency because clock gating could yield much smaller values. The comparison was made while work was running, with a brief request for existing permitted minimum frequencies; the original minimums were restored afterwards.

The structures associated with the alternate PLLs contained post_div_config = 0x100, representing the divide-by-two setting in the reference code. Live symbols from the same running kernel helped locate these structures in the decompressed image. The structure layout was checked against the PLL header, and the treatment of its fields was checked against the alpha PLL implementation.

Each post_div_config value was changed from 256 to zero. In this specific little-endian binary, each change cleared one byte, for two changed bytes in total. Adjacent values were validated as well. Kernel instructions were not patched.

After the correction, E06 measured approximately 1,593.595 MHz for a requested 1,593.6 MHz. E07 and E08 also measured approximately 902.4 MHz on the performance cluster. Computation checks continued to pass. The result connected the suspected divider error to an observed clock and workload effect.

The temporary change needed to read kernel symbol addresses was reversed: kptr_restrict was restored to its original value of 2. This is not a request for other users to leave kernel pointers exposed.

Frequency caps and image construction

The original performance tables included frequencies up to 2,150.4 MHz for the observed speed bin. Early experiments retained only entries at or below 902.4 MHz. Device-tree variants with different frequency steps had a retained maximum of 883.2 MHz; the actual phone used the 902.4 MHz variant.

Each boot payload contained twenty device trees. All three performance speed-bin tables in each were processed, sixty tables total. E08 additionally processed all sixty efficient-cluster speed-bin tables to impose a 1,593.6 MHz upper bound. Retained frequency/voltage pairs were copied without changing voltage values. Every unrelated property was checked for byte equality.

The tables were shortened in place: removed property data was replaced with legal FDT NOP tokens. This preserved each DTB's overall size and the appended DTB sequence. The device-tree specification defines those structural tokens. Independent libfdt reads verified the resulting tables during the original campaign.

The corrected kernel was recompressed with LZ4. Its compressed size changed, so the ramdisk had to be placed at the new page-aligned offset and the kernel-size field updated. The stable image's legacy header ID was recomputed. A separate AOSP unpacker confirmed the payload layout and unchanged ramdisk. The implementation document provides the exact numbers and checks.

No inference about image format was made from the Android release number. This installation ran Android 15 using a legacy header-v0 image; the actual bytes were authoritative for parsing.

E08 was retained with four online CPUs, alternate clock parents, ACD disabled, divide-by-one output settings, and caps of 1,593.6/902.4 MHz. These settings reside in the boot image and were confirmed after repeated normal boots. Runtime frequency-forcing daemons were not installed.

The false log alarm

The first automatic E08 result was marked failed after both load phases had completed successfully. Its kernel-error regular expression searched for Oops: without a word boundary. It therefore matched the substring in a normal ramoops: attached initialization message.

The complete matching line, live log, final log, boot identity, and worker results were reviewed. The original result file was preserved. The expression was corrected to require a word boundary, then the existing logs were checked again. The E08 result was marked passed with an explicit review note; the history was not rewritten to conceal the harness failure.

The public toolkit includes tests showing that normal ramoops registration is accepted while an actual Oops or panic is detected. Error detectors can themselves introduce false conclusions; a failed automation check must be interpreted before it becomes a hardware diagnosis.

What the evidence supports

The strongest supported finding is a dependence on clock-path configuration. Low frequency with the original path was insufficient in E02. The alternate-path configuration allowed both performance CPUs to compute correctly and remain online during the recorded loads. Correcting the dividers changed measured clocks and restored the expected frequency behavior.

The original failing capture had 100 performance-PLL warnings, E02 had 58, and the final boots each retained one early warning around 1.3 seconds. No repeated lock-failure sequence appeared during the successful load runs. The remaining early warning should not be hidden or relabelled as zero errors. It is consistent with the fact that selecting an alternate running path does not remove all primary-clock initialization.

Hardware instability in the normal PLL, its supply, or associated clock logic is a plausible explanation. An ACD-specific problem or a driver/initialization interaction remains plausible too. The experiment did not hold all those factors constant independently, so it cannot rank individual physical components with confidence. A “reflow the CPU” conclusion, a precise solder diagnosis, or a claim that two cores had physically died would exceed the evidence.

Limits and remaining issues

  • One device and one original image were investigated. No second-device replication or controlled comparison with a known-healthy Pixel XL was performed.
  • The retained mode trades peak frequency for a tested operating configuration. This campaign did not establish the highest stable frequency or overall UI speed relative to a healthy stock phone.
  • Sustained operation over days, deep suspend, standby drain, power-off cold starts, radio workloads, camera use, and GPU-heavy applications were not validated by these tests.
  • Battery temperature was monitored, but the reported capacity and cycle fields did not establish battery state of health.
  • The ROM also showed Java exceptions in Google Carrier Services and hotword enrollment. Correct CPU arithmetic does not repair missing providers or application permission problems.
  • An OTA or boot-image replacement can remove the workaround. Reusing this boot image with a different system/vendor build is outside the validated case.

The useful outcome is a recoverable, evidence-backed operating configuration and a method others can test carefully. The next research steps are set out in the research plan.

Intended use

This sequence is for an owner or technician investigating a marlin Pixel XL with symptoms resembling the case study. Begin with identification and evidence. Advance only when the previous state is understood and a tested return path exists.

The included binary builder supports one exact original boot hash. A different hash is a porting task, not an invitation to bypass validation. A matching hash still does not establish that another phone has the same defect.

The owner in the case study accepted experimental recovery and already had an unlocked bootloader. Your data priorities may be different. Bootloader unlocking normally resets user data; changing lock state is outside this toolkit. Consult the AOSP bootloader-locking documentation before considering it. Do not relock a device running an experimental boot image.

Prepare the host and an experiment directory

Install Android SDK Platform Tools from Google's official distribution. Verify that both adb and fastboot are available. The offline image builder additionally needs Python 3.9+ and LZ4; see the tool reference for exact requirements.

Create a private directory outside the public project. Keep original images immutable, give every experiment a new directory, and record full hashes. Do not paste raw collections into a public issue: command lines, persistent logs, device identifiers, and application traces can expose information unrelated to the CPU problem.

In all examples below, replace SERIAL with the selected device's actual serial. Do not omit -s when more than one Android device might be attached.

adb devices -l
fastboot devices

These commands inspect different transports. An Android device visible in ADB may disappear and reappear as a fastboot device during a requested reboot. An empty ADB list alone does not prove that the USB port or phone hardware is dead.

Wait for reconnection and verify id again.

Preserve evidence and the original boot

When root ADB is available, collect a private baseline:

python3 tools/collect.py \
  --serial SERIAL \
  --out ../private/baseline \
  --include-pstore \
  --backup-boot

The tool reads the active slot from Android, backs up that boot partition, and compares the downloaded SHA-256 with a hash computed on the device. It saves the slot and build observations in backup.json. It does not switch slots or flash anything.

If root is unavailable, omit --backup-boot to collect whatever diagnostics are readable. Permission failures are recorded. A partial collection is not a substitute for a known matching boot image and recovery path.

Preserve pstore early. A later reboot or deliberate shutdown can replace the evidence you wanted. In the case study, an intercepted restart yielded logs of the intercepted boot, not a definitive trace of the preceding failure. Never infer a panic simply because a reset occurred.

Record at least:

  • Product, ROM version, kernel release, active slot, and boot hash.
  • Available transports and bootloader lock state.
  • Online/present CPU lists, cluster frequency tables, and clock parents when readable.
  • The count and timestamps of relevant PLL warnings in each captured buffer.
  • Battery temperature, thermal-service status, and whether external power is connected.
  • What the user observed physically and what the tools actually confirmed.

Keep the original backup outside any build output directory. Hashes identify bytes; filenames such as stock.img or fixed.img do not.

Read the failure signature in context

The investigated phone showed repeated perfcl_pll lock failures. Recovery could nevertheless run all four CPUs. A two-core Android boot worked, while adding a performance CPU with only a frequency cap still led to another restart.

Look for that pattern, rather than treating every bootloop as equivalent. A bootloop caused by incompatible system/vendor partitions, missing storage, filesystem damage, or an application/framework problem may need a different investigation. An isolated early PLL warning is not enough: even the retained working image logged one during startup.

Likewise, do not interpret normal ramoops initialization as an Oops. Read the whole line and surrounding timestamps. The included kernel-log summary lists heuristic candidates; it is not an automated hardware verdict.

Build the rescue image only when the original matches

Inspect your backup and compare its hash with the profile:

python3 tools/inspect_boot.py ../private/baseline/boot-original.img

If it is the supported input, build a rescue image in a new output directory:

python3 tools/build_boot.py \
  --boot ../private/baseline/boot-original.img \
  --profile profiles/marlin-lineage22-case1.json \
  --variant rescue \
  --out ../private/rescue-build

The result changes only the header command line to request two CPUs. It preserves the original payload and the original header ID, matching the tested rescue bytes exactly. An unsupported hash causes refusal before a modified image is written.

If the hash differs, stop this binary-reproduction path. Continue with the porting plan, obtain an image that actually belongs to the installation, or rebuild a suitable kernel from known source. Do not substitute the final case image for an unrelated ROM.

Plan installation and rollback before writing

Enter fastboot deliberately, for example from responsive Android:

adb -s SERIAL reboot bootloader

If the device is unresponsive, physical Power/Volume Down entry may be necessary. Software cannot guarantee recovery from a device that no longer exposes a controllable transport.

Read the bootloader state:

fastboot -s SERIAL getvar product
fastboot -s SERIAL getvar current-slot
fastboot -s SERIAL getvar unlocked

The toolkit's planner validates the profiled files and makes read-only fastboot queries:

python3 tools/flash_plan.py \
  --serial SERIAL \
  --profile profiles/marlin-lineage22-case1.json \
  --source-backup ../private/baseline/boot-original.img \
  --image ../private/rescue-build/boot-rescue.img \
  --rollback ../private/rescue-build/boot-rescue.img

For this first installation, the rescue image is a candidate, not yet a proven working rollback on your own device. Preserve the unmodified original separately; it restores the previous image bytes even if the previous behavior was a bootloop. Do not proceed to four-core experiments until the rescue candidate has actually booted and been checked on your device.

The planner prints installation and rollback commands but executes neither. It verifies product, active slot, lock state, partition capacity, and image hashes. Fastboot cannot establish that a supplied backup still belongs to the currently installed system/vendor build; you must establish that from your own records. If the active slot or build changed since the backup, reconcile that change before writing.

For an independently verified active slot a, the deliberate write would look like:

fastboot -s SERIAL flash boot_a ../private/rescue-build/boot-rescue.img
fastboot -s SERIAL reboot

Use the actual verified slot, not a copied from this example. Do not flash both slots as a precaution. Do not switch slots merely because one failed. A/B slots contain related software components, and changing only one component or selecting an incompatible slot can create a different failure. The AOSP A/B implementation documentation explains the slot model.

Do not assume fastboot boot will work. On the case device it rejected the original image too. That observation is specific to this device/bootloader/image combination, not a general statement that Pixel XL can never temporarily boot an image.

Verify the rescue before proceeding

A successful flash command only means the bootloader accepted the write. After Android starts:

  1. Confirm sys.boot_completed=1 and the expected product/build.
  2. Re-establish authorized root ADB if needed.
  3. Hash the active boot partition and compare it with the image just installed.
  4. Read /proc/cmdline, CPU present and online, and actual frequency tables.
  5. Capture dmesg and any available pstore before further reboots.
  6. Run a short, correctness-checked workload on the CPUs that are actually available.

Example for a verified two-core rescue:

python3 tools/soak.py \
  --serial SERIAL \
  --expected-boot-sha256 7c6f9d632f45f5b5000e541cef5ae17b48b496e6d9135e5058578da0748cd8e8 \
  --cores 0,1 \
  --seconds-per-phase 30 \
  --out ../private/rescue-load

The tool assumes the tested battery temperature interface uses tenths of a degree Celsius and that vendor.thermal-engine is running. If your ROM differs, inspect it and port the test rather than defeating its checks.

With a two-core boot restriction, inspect cpusets before attributing every performance problem to damaged silicon. Do not run the private case's old cpuset-adjustment script on a four-core phone. The public toolkit does not ship that device-specific mutation script.

python3 tools/soak.py \

This requests two five-minute phases. It computes expected digests on the host, verifies data copied to the phone, pins a worker to each selected CPU, monitors continuity and temperature, and records the kernel log. It does not force frequency minimums or change thermal settings.

The 40 °C battery cutoff is a conservative experiment policy, not the phone's specified maximum operating temperature. A temperature stop means the test stopped under that policy; it is not proof of a defective CPU. Let the device cool and understand its power/charging conditions before deciding on another test.

Reboots and display transitions

After successful load tests, verify persistence through a few deliberate normal reboots. For each one, record the old boot identity, request adb -s SERIAL reboot, wait for Android, obtain root only through the device's authorized mechanism, and verify the new identity, image hash, online CPUs, limits, parents, and log. Stop if the device fails to return rather than issuing further dependent steps.

Display checks can use input keyevent KEYCODE_SLEEP and KEYCODE_WAKEUP, with dumpsys power to record the resulting state. In the case, the states were Dozing and Awake. Do not call this a deep-suspend test. The original command line already disabled a low-power sleep setting, and USB connection itself can affect power behavior.

Follow the reboots with a short load run using a new output directory. A configuration that worked before a reboot is not automatically proven to have survived it unchanged.

If something fails

Preserve the private worker logs and kernel stream first. Identify whether the failure was a wrong checksum, an unexpected reset, a transport failure, a temperature stop, or a test-harness parsing problem. Those are different observations.

If the device returns in ADB, it may be possible to capture logs and enter fastboot before another reset. If fastboot is already available, use the previously prepared rollback command for the verified active slot. If neither transport is available, physical button entry may be required. The toolkit does not promise unattended recovery from every hang.

Restore the known-working rescue image, boot, and verify its hash and CPU restriction. Do not escalate to higher clocks, disable protection, change random voltages, or switch slots while the preceding failure is unexplained.

Finish with a reproducible record

Record the selected image hash, preserved original, tested rollback, exact ROM observations, test durations and counts, maximum sampled temperature, and remaining limitations. An image should not be described as permanently repaired on the basis of a few successful boots.

python3 tools/export_summary.py \

Two outputs from one original

The public builder reproduces the rescue and retained four-core images directly from the unmodified original. It does not reproduce every intermediate experiment. Intermediate hashes remain in the evidence ledger so a reader can distinguish which result belongs to which image.

The two supported variants are:

  • rescue: append nr_cpus=2 maxcpus=2; preserve all payload bytes and the original legacy header ID.
  • stable: patch the two alternate-PLL divider fields, cap both cluster frequency tables, add the four-core alternate-PLL options, recompress and repack, and recompute the legacy header ID.

The builder checks the complete input hash before interpreting the profile's raw kernel offsets. It then checks the decompressed kernel hash, field-adjacent constants, number of changed bytes, patched raw hash, compression roundtrip, device-tree structure, unrelated properties, ramdisk identity, and complete output hash. The output hash is the final gate before writing the candidate file.

The AOSP boot-image header reference is the format reference; this implementation intentionally handles only a subset.

Command line and legacy ID

The original primary command-line field contained the board and boot-device arguments and lpm_levels.sleep_disabled=1. Its extra command-line field was empty. The toolkit preserves the existing primary arguments, requires the added text to fit the primary 512-byte field, and retains an empty extra field.

The original stored legacy ID did not equal the SHA-1 recomputed from its payloads. The investigation did not determine why. The rescue output preserves it exactly because only the command line changed and the successful rescue image is the reference result.

For the stable repack, the SHA-1 input consists of kernel bytes plus their little-endian length, ramdisk bytes plus their length, and the empty second-stage payload plus its zero length. The digest is stored with the remaining ID bytes padded with zero. Recomputing this legacy field is not signing the image and does not make it acceptable to a locked verified-boot chain.

Device-tree caps

The parser walks the FDT structure tokens and string table. It identifies qcom,pwrcl-speedbin*-v0 and qcom,perfcl-speedbin*-v0 properties, each containing frequency/voltage-corner pairs. For the retained case, it keeps frequencies at or below 1,593,600,000 Hz for pwrcl and 902,400,000 Hz for perfcl.

The actual DTB may use a lower supported step: some variants retain 883.2 MHz in the performance table. The cap is an upper bound, not an invented operating point. The runtime table on the case phone was separately checked.

Removed pairs are replaced with FDT NOP tokens after shortening the property length. Each DTB keeps its original total size. The parser then verifies that the set of property names is unchanged and that every unrelated property value is identical. Retained voltage-corner values are copied exactly.

There are three tables per cluster in each of twenty DTBs, so the final transformation handles 120 tables. The profile records the original DTB offsets and sizes; the builder checks that the sequence is contiguous and accounts for the entire tail of the kernel payload.

During the original campaign, independent upstream libfdt tooling checked the 60 performance tables and, later, the 60 efficient tables. The public builder's own parser is supplemented by tests and by the final byte-for-byte output hash. For an independent port, use another parser such as fdtget as well; two implementations agreeing is more informative than one implementation reading its own output.

Repacking and independent verification

The modified raw kernel was compressed using:

lz4 -12 -B7 -f Image.patched kernel.patched.lz4

The builder decompresses that result and compares all bytes with the intended raw image. It also checks the frame header. The capped DTB tail is appended, the new kernel size is written, and the unchanged ramdisk is placed at the new aligned offset.

The result is padded to the original 32 MiB partition-dump size and its legacy ID recomputed. An independent AOSP unpacker was used during the device campaign. The public package does not redistribute that script; its upstream source is linked in References.

LZ4 output can depend on implementation/version choices. The public builder therefore refuses to write a final image if the complete SHA-256 differs from the validated result, even if a decompression roundtrip passed. Use the recorded tool version or investigate the difference explicitly. Removing the final hash check would change the scope of the tool.

Runtime checks that static image checks cannot replace

An image can be structurally valid and still fail on a phone. The campaign separately checked the installed partition hash, boot completion, CPU availability, actual mux parents, module options, frequency tables, hardware clock measurements under load, correctness workloads, display transitions, and repeated boots.

Reported scaling_cur_freq and clock rate values were insufficient to detect the initial divide-by-two behavior. The debug clock measure interface exposed the difference under load. Conversely, a low measurement while idle was not treated as evidence of a broken frequency setting.

The public soak tool does not modify frequency minimums to perform clock measurements. If a researcher does so manually, record the original settings first, use only supported values, restore them reliably, and continue to respect thermal restrictions. The original campaign restored both cluster minimums to 307,200 kHz.

Why a clean source implementation is still useful

The binary method made a small, auditable intervention possible when the exact compiled source provenance was unknown. A source-built implementation could express the workaround as a deliberate configuration option, document its constraints, and avoid per-build data offsets.

That does not automatically make a rebuilt kernel equivalent. A proper source experiment needs a control build, matching configuration/toolchain, boot and ramdisk compatibility checks, and the same runtime validation. The research plan describes that next step without claiming it has already been completed.

Three different questions

This project keeps three kinds of validation separate:

  1. Image correctness: did a transformation produce the intended bytes without changing unrelated payloads?
  2. Device behavior: did the installed configuration boot, select the intended clocks, and execute the recorded workloads correctly?
  3. Tool correctness: do the newly packaged scripts parse, refuse, record, and clean up as intended in their tested paths?

Exact image hashes answer the first question. Original phone logs and results answer a bounded part of the second. Host tests, including simulated transport, answer part of the third. None is a substitute for the others.

Clock and continuity checks

The original harness compared the installed active-boot SHA-256 to the intended candidate before exercising it. It recorded boot identities to detect unnoticed restarts and sampled online CPUs, frequencies, temperature, thermal-service state, and CPU accounting. E08 main work intervals showed approximately 99.8–100% CPU busy time in the sampled accounting.

Reported frequency was checked separately from hardware clock measurement. Kernel logs and the reviewed false alarm

The campaign preserved live and final dmesg, worker outputs, and result JSON. The main E08 workload completed correctly, but an overly broad Oops: expression matched normal ramoops: attached initialization. Environment and verification scope

The host tools use Python 3.9+ and its standard library. Invoke them with python3 from the project root. The device tools additionally need Google's adb or fastboot on PATH; each accepts an explicit executable path. The stable image builder needs the LZ4 command-line utility. inspect_boot.py: inspect a raw legacy boot image

python3 tools/inspect_boot.py ../private/boot-original.img

Outputs JSON with the complete hash, payload sizes and offsets, command line, stored legacy ID, and whether the ID matches a fresh calculation. It reads only the named host file.

The underlying parser accepts a narrow legacy header-v0 layout with supported page alignment, an empty second-stage payload, zero padding, and a zero trailer. It rejects modern headers and unexplained nonzero trailing data. This strictness is intentional: an unrecognized footer may be meaningful. Inspection does not establish that an image belongs to the connected phone or will boot.

build_boot.py: reproduce a profiled image offline

Required arguments are --boot, --profile, --variant rescue|stable, and --out. Optional --lz4 selects a particular executable. The output directory must not already exist.

The builder writes boot-rescue.img or boot-stable.img and a manifest.json. The manifest records hashes, variant, parser observations, and transformation details; the stable manifest also records LZ4 version and DT changes. There is no ADB or fastboot invocation in the builder. A successful build proves the byte transformation, not a successful boot on another phone. See Implementation for the exact checks and the source image's unusual legacy ID.

The host creates a deterministic data buffer: half pseudorandom bytes, half repeated byte values. It calculates SHA-256 and SHA-512 locally and verifies the uploaded data's SHA-256. The target directory is a unique /dev/pixel-lab-<nonce> path; on the case platform /dev is RAM-backed. Inspect this assumption when porting. Input data plus per-core compressed/decompressed working files consume additional RAM; a 32 MiB buffer does not mean a 32 MiB total footprint.

Each selected CPU receives one pinned worker. Phase hash verifies both digests of the shared data. Phase mixed additionally compresses the buffer, decompresses it to a per-core file, and compares the recovered file's SHA-256. Each successful hash iteration counts as two checks; each mixed iteration counts as three. The known expected values come from the host, so “a command completed” is insufficient to pass.

Workers use device uptime for a deadline, a per-iteration temperature check, a shared STOP file, and an outer timeout of requested phase duration plus 30 seconds. Host monitoring samples approximately every three seconds, with additional command latency. It checks boot continuity, online CPUs, thermal service, temperature, optional reported frequency limits, worker status, and log-stream availability. It imposes a phase watchdog. These checks do not guarantee that every instantaneous clock or temperature excursion is sampled.

Kernel logs are captured before, during, and after load. The current implementation evaluates critical-message candidates and new PLL failures at the end of the completed workload; it does not promise immediate interruption on the first log line. Worker, temperature, continuity, and transport failures are checked during execution. Existing critical messages stop the load before workers start. Existing early PLL warnings are recorded separately; newly observed PLL lock failures cause the run to fail. dmesg -w behavior and readable timestamps are assumptions of the case platform.

Output and stopping behavior

A local run directory contains PRIVATE.txt, journal.jsonl, result.json, generated worker.sh, per-core worker output, and initial/live/final dmesg when available. The temporary host data buffer is removed in cleanup. Raw output includes the device serial and boot UUIDs; keep this directory private.

Journal events are flushed and fsynced. Result JSON is written through a temporary file and rename. On a normal Python exception or Ctrl-C, cleanup requests STOP, allows workers time to finish their current operation, terminates remaining host ADB processes, stops the log stream, and attempts to remove only that run's device directory. device_temporary_files_removed records whether the final device cleanup command succeeded. A successful workload can still need cleanup review.

Host process termination or cable loss does not guarantee instant termination of every device-side helper. Workers retain finite deadlines and outer timeouts; a kernel hang is outside their control. After reconnecting, inspect remaining pixel-lab processes and the exact cleanup_path recorded for the run. Do not use broad deletion patterns. If the host was forcibly killed before finalization, result.json may be missing; the journal is evidence of an incomplete run, not a pass.

A successful run proves the recorded bounded checks completed. It does not test all RAM, storage durability, every instruction, GPU load, radio use, deep suspend, or weeks of uptime. It does not verify hardware clock measurements: the optional frequency guards read cpufreq values, which initially hid the divide-by-two issue in this case.

When a suitable phone is available, compare a new collector snapshot with manually read product, boot hash, slot, online CPUs, and temperature. Verify that requested pstore is captured or its absence is recorded. Check that the boot backup matches the remote hash and remains unchanged.

Run a short public soak on an already-established configuration, then a longer bounded run if results warrant it. Confirm worker affinity and process exit status, sample continuity, and verify temporary-directory cleanup. Check the exported public JSON against the private result. Record exact ADB, Python, and host versions.

Host simulations already exercise success, temperature stop, unexpected boot identity, and worker failure. Do not create a real overheat or corrupt a working boot image merely to test those branches. A deliberately low policy cutoff on an otherwise normal-temperature phone can test refusal behavior; a malformed input file can test offline hash gates. Test higher-risk device events only on an explicitly designated test unit with recovery available.

Extend confidence in the retained phone

The completed load duration is short. A practical follow-up record should distinguish:

  • Normal reboots from fully powered-off starts.
  • Display-off states from actual suspend entry and exit.
  • USB-powered tests from battery-powered use.
  • CPU arithmetic from GPU, camera, media, storage, and radio activity.
  • Thermal stops from checksum failures, resets, application exceptions, and transport disconnects.

Begin with ordinary use and staged, attended load sessions. Increase duration only after the previous stage passes and temperatures settle. For example, a 30-minute requested CPU run fits the current wrapper's two 900-second maximum phases; repeated sessions with cooling and log review give better context than an unattended retry loop. A duration target is a proposed experiment, not a guarantee or a manufacturer specification.

Record charging state, approximate room temperature, screen state, and observed battery temperature. Battery capacity and cycle fields in this case are not trustworthy state-of-health estimates. A controlled discharge experiment is a separate battery investigation and should not be mixed into CPU clock tuning.

Deep suspend needs explicit study because lpm_levels.sleep_disabled=1 was already present in the original image. Do not remove it silently while claiming to reproduce the retained configuration. If a future experiment changes sleep behavior, give that image a new hash and experiment ID, keep the current image as fallback, and measure actual suspend/resume behavior and idle energy.

Reproduce on another device

Use the device report template. Establish the phone's product, installed software, lock state, active slot, original image hash, symptoms, and accessible transports before deciding whether the clock-path hypothesis fits.

For the exact supported source hash, the builder can reproduce the same two images; each device still needs its own recovery baseline and validation. For another source hash, stop the existing binary transformation path. The diagnostic collector can still be useful, but changed offsets and image provenance must be established through a new profile or source implementation.

A useful comparison includes a known-healthy marlin on matching software. Healthy hardware can help determine whether the alternate-PLL divider behavior is a general property of this driver configuration or peculiar to the case installation. Do not assume that a healthy control's working settings are safe for the failing phone.

Avoid transferring entire private logs between strangers. Exchange a reviewed numerical summary, exact image hashes, selected relevant lines, and a completed report. Owners should retain the original full evidence locally.

Port to a different compiled boot image

Prefer a controlled source build when feasible. If binary work is justified, a new profile requires all of the following:

  1. Establish which boot image belongs to the installed system/vendor build and slot. Preserve it unchanged and identify it by full hash.
  2. Parse the actual boot header, compression framing, payload boundaries, appended device trees, and trailing data. Do not force a modern or signed layout through the legacy-v0 parser.
  3. Establish the source structures and their compiled layout for that image. Offsets from this case are not transferable evidence.
  4. Locate each intended field through trustworthy symbols or independently reviewed binary analysis, and verify the surrounding values. Record how address-to-file-offset translation was established.
  5. Confirm the PLL divider interpretation and parent/ACD semantics in that image's driver version. Similar names are insufficient.
  6. Enumerate every relevant device-tree frequency table and retain existing voltage-corner pairs. Check all DTBs that the image can select, not just the first one.
  7. Preserve the ramdisk and every unrelated image component. Independently validate the new structure and DTBs. Do not silently drop a signature or footer.
  8. Give the new profile a distinct ID, input hash, output hashes, source/tool provenance, and tests. Obtain a reviewed recovery plan before physical validation.

Changing source_boot_sha256 in the existing JSON to make the builder accept a different image does not satisfy these requirements. The final output gate also encodes a known result; replacing all expected hashes without validating the transformation defeats the purpose of a profile.

Build a controlled source implementation

Recover the exact ROM build manifest, kernel commit, configuration, compiler/linker versions, and packaging steps if possible. First build a control kernel without the workaround. Determine whether it reproduces the relevant behavior and remains compatible with the installed ramdisk and userspace. Record differences if byte-identical reproduction is unavailable.

A source implementation could expose an explicitly named option for the alternate clock path and corrected divider values, document its interaction with ACD, and apply selected frequency caps in device-specific DT data. Preserve default behavior for unaffected devices unless broader evidence supports a change. Do not turn this single case into a silent global driver default.

Validation should include source review, boot layout and DT inspection, measured clock behavior, arithmetic checks, reboots, and power-state transitions. The old binary profile remains useful as a reproducible historical reference, even if a better source implementation replaces it for new work.

Repeated lock warnings can arise from the clock circuit, its supply, timing/initialization, or related control logic. Software experiments alone cannot conclusively identify a defective solder joint or rail. Frequency exploration comes after stability

The retained performance cap is conservative and was not proven optimal. A future campaign could evaluate additional existing operating points one step at a time, with measured clock verification, identical workloads, thermal records, a new image hash per step, and rollback after any correctness or continuity failure.

Do not infer permission to raise voltage, disable mitigation, or remove the DT limits from this plan. Keep voltage entries and thermal behavior unchanged when testing a frequency hypothesis. An apparent speed increase without clock measurement and correctness checks can repeat the divide-by-two misunderstanding.

Performance reporting should distinguish per-core throughput, aggregate throughput, UI behavior, and energy. Use multiple repeated runs under comparable starting temperature and background activity. The earlier approximately 21% SHA improvement on the two-core system does not estimate whole-phone improvement from E08.

Reporting and release milestones

The first public package can accurately be described as a single-device case study with an exact-image reconstruction toolkit. It should not be advertised as a universal repair, a newly discovered physical defect, or an exhaustive comparison with earlier community work.

A later release should state what changed, whether new tools were actually run on hardware, which original hashes are supported, and which failures remain. Keep a changelog. Preserve old result files when a parser bug is corrected and add a review note, as was done for the ramoops false alarm.

Pixel XL bootloop case: recovering four cores through an alternate clock path

We investigated a first-generation Pixel XL (marlin) that had been unused for years and repeatedly failed to stay in Android. The original failed-boot console contained 100 perfcl_pll lock warnings. Recovery could still run all four CPUs, so the evidence did not support simply declaring the two performance cores dead.

A boot image restricted to CPU0/1 first restored a usable Android session. Capping the performance cluster near 902 MHz and enabling CPU2 on the original clock path still produced repeated warnings and another restart. Switching both clusters to the driver's alternate PLL mode, with ACD disabled as required by that mode, allowed all four cores to execute correct workloads.

There was another finding: the alternate path initially ran at half its reported frequency. Clock measurements under load exposed a divide-by-two setting. Correcting two data bytes in the decompressed kernel restored measured rates to the intended values. The retained image also caps CPU0/1 at 1,593.6 MHz and CPU2/3 at 902.4 MHz, preserving retained voltage entries and thermal settings.

The selected configuration completed 7,252 checksum/compression checks over approximately twelve minutes of requested load, 800,000 floating-point iterations across four cores, three normal reboots, and ten display Dozing/Awake transitions. Maximum sampled battery temperature during its load runs was 39.0 °C. One early PLL warning remained; the repeated failure sequence did not recur in those runs.

This is one device, not a universal fix or a proven diagnosis of a particular physical defect. The PLL path and ACD mode changed together, and the exact compiled kernel provenance remains unknown. Deep suspend, days of reliability, and a second-device reproduction remain open work.

The accompanying package contains the full experiment sequence, failed approaches, sanitized numerical evidence, a recovery/rollback runbook, an exact-input boot builder, diagnostic collection, a bounded per-core load tool, host tests, and a research plan. The builder accepts only one full original-image SHA-256 and reproduces the two validated case images byte-for-byte. No firmware binaries or personal device identifiers are distributed.

The device campaign used a private harness. The refactored public scripts have host tests and exact reconstruction checks; their new ADB wrappers still need a fresh hardware validation. The documentation also preserves a useful harness mistake: Oops: incorrectly matched normal ramoops initialization until the detector was fixed and the original results were reviewed.

We would welcome carefully documented independent reports, especially comparisons that help separate clock-parent and ACD effects. Start with the included README and device-report template. Do not bypass the image hash checks or transfer raw offsets to a different build.

Read the documentation and get the tools at westman2000/pixel-xl-recovery, or download the latest release. Share reviewed results through the repository's report template.
